# V15 石闩机关规则核查

核查日期：2026-09-13。对象为原版 `26.3-snapshot-9` 的 S3 单黏性活塞石闩。采用本机原始 JAR 的 `javap -c -p`（必要时 `-v -p`）和 Minecraft 官方资料。没有运行游戏或服务器，没有修改 JAR、存档、NBT、生成器或其他项目文件。下文是规则证据和坐标推导，**不是游戏内开关、通行或重进验收**。

## 结论

- 拟议石闩的两个稳态成立：活塞 `(55,5,32)` 向下；关闭时头在 Y4、雕纹砂岩在 Y3；打开时活塞回缩，砂岩回到 Y4，Y3 清空。稳态活塞头必须为 `type=sticky,short=false,facing=down`，不是只给活塞本体填 `extended=true`。
- 主实现提出的远程拉杆→7 格上坡线→向西输出的中继器→满块→墙火把反相路径成立。所列元件之间没有发现直接供电或准连接旁路；这以全部邻域和支撑符合下文条件为前提。
- 两处爬坡额外气格 `(59,4,26)`、`(59,5,27)` 必须保留。活塞不能只查六邻；上方五个准连接源格也必须查，详见 E 节。
- 拉杆是保持开关，不能以快速短脉冲操作。完整伸出之前撤电存在“不拉回石块”的事件分支。每次拨动后等运动完成再操作，不把紧接着拨回的结果当作本机关保证。
- 地板方块在 Y1 意味着脚底高度为 2。Y3 砂岩留下 1 格净高，挡住默认尺寸的站立和蹲伏玩家；爬行姿态高度约 0.6，不能据此声明禁止爬行。三格宽地板必须在门框收为一格，否则可从闩左右绕行。

## B. 稳态、正常放置与伸缩位置

所有坐标为世界方块坐标，P=`(55,5,32)`，D=`down`。本体方块是 `minecraft:sticky_piston`，其状态只有 `facing` 和 `extended`；`type`、`short` 属于 `minecraft:piston_head`，不能写到本体上。

| 位置 | 关闭稳态：拉杆 off | 打开稳态：拉杆 on |
|---|---|---|
| `(55,5,32)` | `sticky_piston[facing=down,extended=true]` | `sticky_piston[facing=down,extended=false]` |
| `(55,4,32)` | `piston_head[facing=down,type=sticky,short=false]` | `chiseled_sandstone` |
| `(55,3,32)` | `chiseled_sandstone` | `air` |
| `(55,2,32)` | `air` | `air` |
| `(55,1,32)` | 连续满块地板 | 同一地板 |

原始证据：

1. `PistonBaseBlock.getStateForPlacement` 偏移 0–33：取最近看向方向的反方向作为 FACING，并明确把 EXTENDED 设为 false。正常放置一个向下活塞不是直接得到闭合表：需让玩家近似向上看着放置，并给它真实供电使其伸出。
2. `setPlacedBy`、`neighborChanged`、`onPlace` 在服务器侧调用 `checkIfExtend`。后者偏移 22–73 在有电、未伸出且结构可推时排入伸出事件；76–223 在无电且已伸出时排入回缩事件。
3. `PistonStructureResolver` 构造偏移 39–76：伸出从 `P+D` 开始，移动方向 D；回缩从 `P+2D` 开始，移动方向 `opposite(D)`。因此起始 Y4 的石块伸出到 Y3，回缩从 Y3 拉回 Y4。
4. `PistonBaseBlock.moveBlocks` 偏移 7–42：回缩先清除 `P+D` 的原活塞头，再解析移动。468–598：伸出时在 `P+D` 创建活塞头的移动过程，其目标状态来自头的默认状态，只设置 FACING 和 TYPE。`PistonHeadBlock` 构造偏移 40–53 的默认 SHORT=false，故正常完成后的头不是 short=true。
5. `PistonHeadBlock.isFittingBase` 偏移 0–69：sticky 头要求后方是黏性活塞，本体 extended=true 且朝向相同。`canSurvive` 向 FACING 的反方向检查本体；向下头的本体应在正上方。缺头、错 type 或朝向相反都不等于正常闭合机关。
6. `PistonMovingBlockEntity.tick` 偏移 196–242 每次增加进度 0.5；进度完成后偏移 51–192 移除移动方块实体并写回目标方块状态、发邻居更新。运动过程中可能出现 `moving_piston` 和方块实体，不能把运动中间态画成最终成品。

建议正常施工次序：先把输入拉杆设 on，让火把确实熄灭并等稳定；放置未通电的向下黏性活塞，再放 Y4 砂岩，确认 Y3 空；最后拨回 off，等待完整伸出，得到默认关闭表。若生成静态结构，应按闭合表生成相互一致的最终状态，但这不等于已经执行了正常放置和邻居事件。

## C. 雕纹砂岩、侧墙与短脉冲边界

`Blocks` 静态注册偏移 4289–4319：CHISELED_SANDSTONE 使用普通 `Properties.of()`，强度 0.8，未改 pushReaction。`BlockBehaviour.Properties` 构造偏移 73–77 默认是本版名为 `PushReaction.PUSH_PULL` 的反应。`PistonBaseBlock.isPushable` 检查世界范围、不可移动特例、硬度 -1、反应和方块实体；雕纹砂岩是普通满块，无该方法的特殊排除。回缩事件 `triggerEvent` 偏移 431–500 允许这个可移动且 PUSH_PULL 的目标被拉回。这里没有“朝下就拉不动砂岩”的额外规则。

单块雕纹砂岩不拉侧墙。`PistonStructureResolver.isSticky` 只识别 SLIME_BLOCK 和 HONEY_BLOCK；`resolve` 偏移 135–157 只对移动集合中自身为黏性块的格调用 `addBranchingBlocks`。`addBlockLine` 的反向粘连扫描也从自身 isSticky 条件开始。不能把“黏性活塞能拉目标”误读成“目标砂岩会粘住旁边所有方块”。固定侧柱可贴着砂岩行程的水平两侧。

为使移动集合一直只有一块，设计检查仍应排除 Y3/Y4 行程六邻的黏液块、蜂蜜块以及其他正在运动的黏性结构；不需要把普通侧柱全部挖空。这是避免今后接入另一种结构的保守设计要求，**不是声称一个静止相邻黏液块必然会被非黏性的砂岩带走**。

必须保持：打开时 Y3 无杂块，Y4 为唯一闩石；关闭时 Y4 为合法头、Y3 为唯一闩石；Y2 空。若打开时又在 Y3 塞进满块，下一次关闭可能把额外方块继续推向 Y2，而非保持原来的一块行程。不要在行程内安放红石、火把、梯子、装饰或方块实体。

短脉冲有明确例外：`checkIfExtend` 偏移 117–208 在前方两格仍为同向、正在伸出的移动活塞且进度或 tick 条件命中时，将回缩事件从 1 改为 2。`triggerEvent` 偏移 425–500 只有事件 1 才进入正常拉块分支；事件 2 会走移除头、不拉回目标的分支。事件执行前还会在偏移 35–84 重查供电，取消已过时的伸缩事件。因此不能以“拉杆能保持”推出“任意快速切换都可靠”。

使用规则：每次切换后等活塞、石块和火把完全稳定再切换；在 20 TPS 条件下，留约 1 秒人为间隔是充裕的操作建议，不是服务器卡顿时的墙钟保证。红石火把另有烧毁机制：`RedstoneTorchBlock.tick` 清除超过 60 游戏刻的切换记录，`isToggledTooFrequently` 到 8 次关断判为过频，烧毁后安排 160 游戏刻恢复检查。S3 不应加入时钟、观察者脉冲或快速反复切换。

## D. 远程拉杆、上坡线与反相火把

主实现提出的坐标如下；这里核查其逻辑，没有确认实际模型已经按表施工。

| 元件 | 坐标与状态/约束 |
|---|---|
| 拉杆 L | `(57,3,26)`，`face=wall,facing=west,powered=false` 初始 |
| 拉杆座 A | `(58,3,26)`，普通可导电满块，西面支持拉杆 |
| W0 | `(59,3,26)`；下支撑 `(59,2,26)` |
| W1 | `(59,4,27)`；下支撑 `(59,3,27)` |
| W2 | `(59,5,28)`；下支撑 `(59,4,28)` |
| W3…W6 | `(59,5,29)`、`(59,5,30)`、`(59,5,31)`、`(59,5,32)`；各自 Y4 下支撑 |
| 中继器 R | `(58,5,32)`，`facing=east,delay=1,locked=false`；下支撑 `(58,4,32)` |
| 火把附着满块 C | `(57,5,32)`，普通可导电满块 |
| 墙火把 T | `(56,5,32)`，`redstone_wall_torch[facing=west,lit=true]` 初始，附着其东面的 C |
| 黏性活塞 P | `(55,5,32)`，向下；T 是其东侧六面邻居 |

供电链的本机证据：

1. `LeverBlock.getDirectSignal` 偏移 0–29 在 powered=true 且查询方向等于 `getConnectedDirection` 时给 15。`FaceAttachedHorizontalDirectionalBlock.getConnectedDirection` 的 wall 分支返回 FACING。A 从西邻 L 查询传 WEST，与 L 的 west 一致，所以 A 被**强充能**。`SignalGetter.getSignal` 偏移 17–38 把导电满块周围的 direct signal 纳入其输出；W0 可从西邻 A 读到信号。不是让一串普通石头无限导电。官方拉杆文章同样说明拉杆会保持开关并供电给其附着块。[官方拉杆文章](https://www.minecraft.net/en-us/article/taking-inventory--lever)。
2. `RedstoneWireBlock.getBlockSignal` 读取邻居信号。`getConnectingSide` 四参数重载偏移 17–88 和 `RedstoneWireEvaluator.getIncomingWireSignal` 偏移 67–155 支持沿导电满块台阶上下连线，但低线头顶不能是导电满块。本方案把 `(59,4,26)`、`(59,5,27)` 明确保留为空气；W0→W1、W1→W2 各升一格，其余平接。下支撑采用普通满块，不能未经复核改为楼梯或装饰半砖。
3. `RedstoneWireEvaluator.getIncomingWireSignal` 末尾偏移 158–165 将相邻线信号减 1。在只有所列输入、无其他电源时，on 稳态 W0…W6 应为 15、14、13、12、11、10、9，足够触发 R。off 稳态应全为 0。填一个 `power=15` 外观不代表存在真实电源。
4. `DiodeBlock.getInputSignal` 偏移 0–25 从 `R.relative(FACING)` 读输入，所以本例 facing=east 读取 `(59,5,32)`；实际输出为反方向西邻 C。`getDirectSignal` 委托方向性 `getSignal`，因此 R 能强充能 C。R 的两个侧输入位置 `(58,5,31)`、`(58,5,33)` 不得放可锁定它的有电二极管组件。
5. `RedstoneWallTorchBlock.hasNeighborSignal` 偏移 0–27 从 `T.relative(FACING.opposite)` 读取附着块，即东面的 C。`RedstoneTorchBlock.neighborChanged` 偏移 23–41 在需要转换时安排 2 游戏刻检查；`tick` 偏移 76–187 有输入时灭、无输入且未烧毁时亮。这就是反相。官方教育材料也把火把描述为反转输入；它只作一般逻辑说明，不用教育版证明 Java 准连接。[官方 Logic Gates，第 3 页](https://education.minecraft.net/lessonsupportfiles/Microsoft-Workshop-Logic-Gates.pdf)。
6. `RedstoneWallTorchBlock.getSignal` 偏移 0–23 只排除查询方向等于 FACING 的附着侧，其余方向返回 ownSignal；亮时 ownSignal=15。P 从东邻 T 查询方向 EAST，而 T.facing=WEST，故 P 确实能读到 T 的 15。墙火把没有装在活塞身上。

真值关系为：L off → W=0 → R off → C 无输入 → T lit → P extended；L on → W 有电 → R on → C 强充能 → T unlit → P retracted。两次切换均需等待中继器、火把和活塞的事件完成。

返馈检查：所列输入线全部在 X59，C 在 X57，T 在 X56；输入不穿过 T 或活塞邻域。中继器阻止 C 向东倒灌回输入。C 的六邻为 `(56,5,32)=T`、`(58,5,32)=R`、`(57,4,32)`、`(57,6,32)`、`(57,5,31)`、`(57,5,33)`，其中只允许 R 为预期外来强信号。不要在 T 上方、C 上方及二者周围补连新的红石线；火把向上的强充能若经导线回到 C，可能变成反馈电路。现表没有这条回路。

## E. 活塞准连接与必须查的邻域

`PistonBaseBlock.getNeighborSignal` 的检查并非“活塞六邻任意有电”这么简单：

- 偏移 0–55 查 P 六个方向，跳过活塞朝向 D；向下活塞跳过下邻。
- 偏移 58–72 另查 `hasSignal(P,DOWN)`，即本体位置的信号，而不是 `P.below()`。
- 偏移 73–139 取 P 正上方，再查其六邻并跳过 DOWN。这是本版准连接来源；上方中心格本身有没有放实体方块不影响这段位置计算。

P=`(55,5,32)` 的完整查询集合：

| 类别 | 源坐标 | 给源的方向参数 |
|---|---|---|
| 直接西邻 | `(54,5,32)` | WEST |
| 直接东邻 | `(56,5,32)`，预期 T | EAST |
| 直接北邻 | `(55,5,31)` | NORTH |
| 直接南邻 | `(55,5,33)` | SOUTH |
| 直接上邻 | `(55,6,32)` | UP |
| 本体查询 | `(55,5,32)` | DOWN |
| 准连接西 | `(54,6,32)` | WEST |
| 准连接东 | `(56,6,32)` | EAST |
| 准连接北 | `(55,6,31)` | NORTH |
| 准连接南 | `(55,6,33)` | SOUTH |
| 准连接上 | `(55,7,32)` | UP |

`SignalGetter.hasSignal/getSignal` 会考虑源本身的方向信号，若源为导电满块，再合并其六邻 direct signal。因此每一个被填成导电装饰块的源格 Q，还必须展开检查 `Q+(±1,0,0)`、`Q+(0,±1,0)`、`Q+(0,0,±1)`，确认没有拉杆、红石线、中继器或火把从正确方向强充能它。只查“没有红石线贴着 P”不够。`Blocks.pistonProperties` 偏移 14–19 的 isRedstoneConductor 谓词，经 `javap -v` BootstrapMethods 第 5 项核对为 `Blocks.never`；正常活塞本体自身不作为导电满块扩展这条查询。

最容易审查的电路隔离方案，是把表中除 P、T 外的 **9 个源格全部保留为空气**；建筑若需要顶盖或侧壁占用其中某格，可以使用已验证的无电结构，但要执行上述六邻展开检查，不能宣称这些格“任意实心块都安全”。尤其 `(56,6,32)`：它既是 T 的正上方，也是准连接东源。火把 lit 时会向上强充能普通满块；这条电路与 T 同开同关，本身不违反稳态，但留空气更容易排除额外输入。`RedstoneTorchBlock.getDirectSignal` 只在查询 DOWN 时提供强信号，正对应火把向上方方块供电。

输入线下方的支撑会被线向下强充能，但所列支撑在 X59，未直接进入这份 P 查询集合。C=`(57,5,32)` 也不在该集合内；它不能隔着已经熄灭的非导电墙火把 T，把信号继续传给 P。这是本方案能反相的关键。

同样，R 下支撑及其两侧应检查是否触发别的机关；这份局部规则核查没有证明与整堡旧音乐线路完全隔离。实际施工必须把新增元件、可被强充能的支撑、邻居更新范围和旧线路一并核对。

## F. 通道与保护布局的静态检查

下面是完整空间检查要求，不能仅靠可达节点图代替人物碰撞验证：

- 闩列 `(55,2,32)` 始终空，`(55,3,32)` 只在打开状态为空；前后 `(55,2,31)`、`(55,3,31)`、`(55,2,33)`、`(55,3,33)` 至少要能接入连续通行体积。若附近是转弯、台阶或非满格门框，检查整个人物扫掠范围。
- 三格宽地板 X54…56 必须在 Z32 收口：固定边柱至少阻断 `(54,2,32)`、`(54,3,32)`、`(56,2,32)`、`(56,3,32)` 的可绕行路径，并接到侧墙。否则单闩仅挡住中央一格。
- 行程侧面 Y3/Y4 可以为普通固定石柱，不要求空气；核实它们不带黏液/蜂蜜，不覆盖拉回目标 `(55,4,32)`。Y4 是头或石，不能加横梁贯穿。
- 默认玩家尺寸来自 `Avatar` 静态初始化：站立 0.6×1.8（偏移 21–48），蹲伏 0.6×1.5（126–156），游泳姿态 0.6×0.6（90–105）。`Player` 的姿态检查也有站立/蹲伏放不下时选游泳姿态的分支。一格净高能挡站立/蹲伏，但可能被已经进入爬行姿态的玩家通过；关闭时运动石块也不能视为对站在闩下的人绝对安全。
- 拉杆在 `(57,3,26)`，是否只能从内侧到达、能否从关闭入口伸手点到、常规长路线是否始终可走，应由实际路线与碰撞/触及测试确认。此机关是探索动线开关，不是权限锁或防拆设施。

## G. 开关循环、保存与重新进入

| 阶段 | 应核对的稳定结果 |
|---|---|
| 默认关闭 | L=false；W0…W6=0；R=false；T=true；P=true；Y4 头、Y3 石 |
| 内侧开启并保持 | L=true；W0…W6 有真实信号；R=true；T=false；P=false；Y4 石、Y3 空 |
| 再次关闭 | L=false；线路最终归零；T 重亮；P 再次完整伸出；回到第一行 |
| 再次打开 | 重复第二行，无石块遗留在 Y3、无多余被推块 |
| 各稳态保存重进 | 应恢复该行块状态；等正常更新后仍符合该行；再操作一次确认可继续循环 |

保持依据：`LeverBlock.pull` 只切换 POWERED、更新方块和邻居，没有按钮式定时复位。稳态记忆保存在方块状态中，不依赖常驻运行的计时器或隐藏记分板。

存储依据：`SerializableChunkData.write` 偏移 218–229 用 blockStatesContainerCodec 写入 section 的 `block_states`；`parse` 偏移 445–449、527–554 用对应 codec 读回。`PalettedContainerFactory.create` 偏移 52–57 使用 `BlockState.CODEC`。拉杆 POWERED、火把 LIT、活塞 EXTENDED/FACING、头 TYPE/SHORT 均是已经注册的方块状态属性，正常区块保存并不会把这些状态一律重置成默认值。

边界：这证明有保存这些稳态数据的代码路径，**不能证明当前 S3 已通过重进测试**，也不保证人工拼成互相矛盾的状态在载入时无条件自愈。若在移动中存档，`PistonMovingBlockEntity.saveAdditional/loadAdditional` 还要保存/读回 `blockState`、`facing`、`progress`、`extending`、`source`；仅拷贝 moving_piston 方块名会丢失必要数据。本次只推荐、核查运动结束后的稳态快照，不承诺半途中退出、区块边界卸载或外服修改红石规则的结果。

后续实际验收应依次做默认关闭→内侧开启→开放状态双向通过→再次关闭→再次开启；在开、关两种稳态各保存并重新进入一次，复查方块和开关，再验证一次循环。还需核实旧音乐电路不受影响。本次没有执行任何游戏内步骤。

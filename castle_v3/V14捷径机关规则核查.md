# V14 捷径机关规则核查

核查日期：2026-09-13。范围仅为原版 `26.3-snapshot-9` 的铁门、铁活板门、拉杆、中继器及相关供电、攀爬规则；使用本机原始 JAR 的 `javap -c -p` 字节码和 Minecraft 官方说明。**没有启动游戏或服务器，没有修改 JAR、存档、NBT 或主生成器，也没有进行实机测试。**

## 结论先行

1. 铁活板门可以成为梯子顶部的可攀爬格，但必须已经打开、正下方紧贴普通梯子，且两者 `facing` 完全相同。检查代码不区分木制或铁制活板门；不是“任意竖起来的活板门都能爬”。见下文证据 C。
2. 铁门与铁活板门不能直接手开；可以用一个保持开启状态的拉杆持续供电。无电默认关闭、有电打开，拉杆再拨回去会关闭，**这不是不可逆的永久解锁**。见证据 A、B。
3. 不要求红石火把。中继器输出端指向门边的导电实心方块，该方块与门任一半格六面邻接，能够通过强充能为门提供信号。不要用玻璃、楼梯、半砖等未经验证的非导电装饰块替代这个供电块。见证据 D。
4. 本版中继器的 `facing` 属性指向**输入侧**，与真正信号流向相反。中继器 `(0,0,0)`、输入 `(0,0,-1)`、输出 `(0,0,1)`，应当使用 `facing=north`。这是输入读取、输出更新、放置及模型四项交叉核对的结果，不是把 `getSignal` 的查询方向误认为信号流向。见证据 E。
5. 带电红石线放在 `(x,34,z)`，其下 `(x,33,z)` 为导电实心方块时，这个支撑块会被强充能；与支撑块同 Y、六面邻接的铁活板门能够收到信号。水平线形不影响向下给支撑块供电的这个分支。前提仍是红石线本身确实有电。见证据 F。

## A. 铁门与铁活板门的开关规则

以下均来自上述本机 JAR，而非网页通用攻略。

| 原始类 / 方法 | 已核查行为与定位 |
|---|---|
| `net.minecraft.world.level.block.state.properties.BlockSetType` 静态初始化 | `iron` 构造在偏移 34–79；三个布尔参数全为 false。完整构造方法偏移 9–22 明确把前两个分别写入 `canOpenByHand`、`canOpenByWindCharge`。 |
| `DoorBlock.useWithoutItem` | 偏移 0–13 先读 `type.canOpenByHand()`；为 false 时返回 PASS，不进入 `OPEN` 切换。 |
| `TrapDoorBlock.useWithoutItem` | 同样在偏移 0–13 检查手开权限；不允许时直接返回。 |
| `DoorBlock.neighborChanged` | 偏移 0–46 检查自身位置和另一半门的位置有无邻居信号。电源状态改变时，偏移 125–157 把 `POWERED` 与 `OPEN` 都设为当前供电结果。来自同门块的部分递归更新会被跳过。 |
| `DoorBlock.updateShape` | 垂直方向连接另一半门时，偏移 52–89 复制另一半状态并保留本半的 HALF 值；因此门必须完整具有上下两半，不能只放单格模型。 |
| `DoorBlock.canSurvive` | 下半门要求正下方方块上表面坚固；上半要求其下为相应门块。 |
| `TrapDoorBlock.neighborChanged` | 服务器侧偏移 8–30 读取自身位置的邻居信号并与旧 POWERED 比较；改变后偏移 33–94 更新 OPEN 与 POWERED。它没有铁门的“另一半门”检查。 |

由此可得：正常从无电、`open=false,powered=false` 开始，通过拉杆通电使其打开，断电使其关闭。这里描述的是**正常放置并收到邻居更新后的行为**，不保证手工编辑出互相矛盾的 OPEN/POWERED NBT 在没有更新时自行修正。

官方一般说明与本机逻辑一致：铁门、铁活板门需要红石控制，木门可手开。官方文章中的“pulse”不是“给一个短脉冲以后永远打开”的承诺，持续状态以本机 `neighborChanged` 为准。[Taking Inventory: Door](https://www.minecraft.net/en-us/article/taking-inventory--door)，[Taking Inventory: Trapdoor](https://www.minecraft.net/en-us/article/taking-inventory-trapdoor)。

## B. 单拉杆为何可以保持开启

`net.minecraft.world.level.block.LeverBlock`：

- `pull` 偏移 0–24：切换 POWERED，调用 `setBlockAndUpdate`、`updateNeighbours`。该方法没有按钮式延时复位调度。
- `ownSignal`：POWERED 为 true 输出 15，否则 0。`BlockBehaviour.getSignal` 的默认实现调用 `ownSignal`，所以拉杆可为邻接组件提供常规信号。
- `getDirectSignal` 偏移 0–29：有电并满足连接方向才输出 15，供电给其附着方块。
- `updateNeighbours` 偏移 44–62：更新拉杆所在位置及附着方块位置的邻居。
- `onExplosionHit` 在可触发方块的爆炸条件下会调用 `pull`；因此暴露的拉杆并非不能被风弹等外部交互改变。

设计推论：可把拉杆放在普通探索路线可达的内侧控制台，默认关闭。玩家经长路线到达后拨到“开”，捷径便持续可用，直至再次拨回或电源被改变。要避免误关和被锁在门外，常规长路线必须一直可走，拉杆不应在关门后不可达的封闭小室中。

官方拉杆说明同样描述再次操作切换开关，并能供电给邻接红石与附着方块。[Taking Inventory: Lever](https://www.minecraft.net/en-us/article/taking-inventory--lever)。官方 1.20.3 说明提到风爆可翻动拉杆，铁门/铁活板门不直接被风爆翻动；本机 IRON 标志与 Lever 方法提供目标版本复核。[Minecraft Java Edition 1.20.3](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-20-3)。

这是一种游览动线上的“从另一侧解锁”，**不是权限锁或防熊系统**。本核查没有验证防拆方块、从外侧另放电源、玩家触及距离、投射物或服务器插件等限制。

## C. 铁活板门与梯子衔接

直接证据为 `net.minecraft.world.entity.LivingEntity`：

| 方法 | 字节码条件 |
|---|---|
| `onClimbable()` | 偏移 58–86：当前位置为 `TrapDoorBlock` 的实例时，调用 `trapdoorUsableAsLadder`。判断的是类，不是只列出木活板门。 |
| `trapdoorUsableAsLadder(BlockPos, BlockState)` | 偏移 0–13 要求 OPEN 为 true；16–35 取正下方方块并检查为 `Blocks.LADDER`；38–56 比较该梯子的 FACING 与活板门 FACING 相同。无铁材质排除，也不另检查 HALF 或 POWERED。 |
| `LadderBlock.canSurvive` / `canAttachTo` | 梯子在 FACING 的反方向找背板，要求背板对着梯子的面坚固。梯子不能只是悬在空气中。 |

可以采用：下方连续梯子，每格同向且有背板，顶部一格同向铁活板门，先供电翻开，再沿原梯子攀过该格。顶部不要用“另一扇活板门”替代紧贴的最后一级普通梯子；本规则明确检查的是正下方 `Blocks.LADDER`。

这只证明目标活板门格会被判为可攀爬，不等于证明整个井道可通行。井口两侧平台、人物碰撞体、顶部转身空间、梯子背板与打开后门片位置都必须由实际坐标验证。关闭的铁活板门不满足上述攀爬分支，并提供闭合门片；其上不能用装饰物把出口占满。

官方活板门文章只泛述活板门能作为梯子；精确的三项条件以本机上述方法为证。[Taking Inventory: Trapdoor](https://www.minecraft.net/en-us/article/taking-inventory-trapdoor)。

## D. 中继器能否直接强充能门边实心块

可以，不必为了开铁门额外加反相火把。证据链全部在本机 JAR：

1. `DiodeBlock.ownSignal`、`getOutputSignal`：中继器 POWERED 时输出为 15；`shouldTurnOn` 对输入值大于 0 判为开启。
2. `DiodeBlock.getSignal`：仅输出方向对应的查询返回 ownSignal；`getDirectSignal` 偏移 0–8 使用同一方向性的输出，因此能够强充能其前方导电块。
3. `SignalGetter.getDirectSignalTo`：从目标块的六个相邻格收集 direct signal 的最大值。
4. `SignalGetter.getSignal` 偏移 17–38：目标方块 `isRedstoneConductor` 为 true 时，将其本身信号与 `getDirectSignalTo` 合并。
5. `SignalGetter.hasNeighborSignal` 检查接收块六面邻居的 `getSignal`；铁门和活板门由此能读取到旁边导电块的信号。
6. `DiodeBlock.updateNeighborsInFront` 偏移 12–54：更新真正输出位置，并通知该位置周围除输入来向外的邻居。因此相邻铁门的更新不是只靠期待随机刷新。

导电块应直接与门的某半格六面相邻；斜对角不算，也不能假设把任意多个普通实心块串起来会无限传电。单中继器 `delay=1` 的延时由 `RepeaterBlock.getDelay` 计算为 2 个游戏刻；这里只设计稳态开关，不设计脉冲竞争、延时锁或特殊更新顺序。中继器侧面有二极管信号可被锁定（`RepeaterBlock.isLocked`、`sideInputDiodesOnly`），新机关应避开这类侧输入。

## E. 中继器朝向：独立坐标复核

令中继器坐标 R 为 `(0,0,0)`，希望输入在北侧 `(0,0,-1)`，输出在南侧 `(0,0,1)`：

| 检查项 | 本机实读结果 |
|---|---|
| `DiodeBlock.getInputSignal` 偏移 0–25 | 直接取 `R.relative(FACING)` 的方块作为输入。故输入北侧要求 `FACING=NORTH`。 |
| `DiodeBlock.updateNeighborsInFront` 偏移 0–21 | 输出更新位置为 `R.relative(FACING.getOpposite())`。NORTH 的相反方向 SOUTH，正好为 `(0,0,1)`。 |
| `DiodeBlock.getStateForPlacement` 偏移 0–17 | FACING 设置为玩家水平放置方向的相反方向；玩家朝南摆放时，属性为 north。`RepeaterBlock.getStateForPlacement` 调用这个基类实现，再设置 LOCKED。 |
| `SignalGetter.getDirectSignalTo` | 接收块从北邻读取 source 时传入 NORTH，方向参数是“从接收位置到被查询的源”；不应把该参数误读为源向北输出。 |
| `assets/minecraft/blockstates/repeater.json` | `facing=north` 的模型绕 Y 轴旋转 180°；south 为默认无旋转，west 为 90°，east 为 270°。 |
| `assets/minecraft/models/block/repeater_1tick.json` / `repeater_4tick.json` | 默认模型固定火把位于局部 Z=2…4；可调火把由 Z=6…8 移到 Z=12…14。north 的 180° 旋转使固定端位于世界南侧，和代码输出端一致。模型顶面使用 `assets/minecraft/textures/block/repeater.png`，本次从原 JAR 内存读取并查看；没有修改纹理。 |

结论：上述坐标例子用 `facing=north`。若方向改成向东输出，用 `facing=west`；向西输出用 east；向北输出用 south。

这里核查的是原版中继器属性。若项目图例的箭头用了自己的“信号方向”定义，需要做显式转换。**不要据此直接批量翻转原有音乐 NBT**：既有音乐结构是否有方向问题需要另行逐段对照实际输入、输出坐标，本核查未检查所有旧音乐线路。

## F. Y=34 导线经 Y=33 支撑块触发相邻活板门

示例：带电红石线 W=`(0,34,0)`，导电实心支撑 C=`(0,33,0)`，铁活板门 T=`(1,33,0)`。T 与 W 斜对角，但 T 与 C 东西相邻。

1. C 的 `getDirectSignalTo` 从正上方 W 查询，传入 `Direction.UP`。
2. `RedstoneWireBlock.getDirectSignal` 偏移 0–17：正常 `shouldSignal=true` 时委托给 `getSignal`。
3. `RedstoneWireBlock.getSignal` 偏移 0–16 排除的是查询参数 DOWN，不是 UP；33–78 在 UP 分支直接返回线的 ownSignal，不要求水平连接形状。`ownSignal` 取 POWER 属性。
4. 因此 C 得到 W 的 direct signal；C 作为导电块又经 `SignalGetter.getSignal` 把它提供给邻接 T。T 的 `TrapDoorBlock.neighborChanged` 得到 true 后打开并设 POWERED。
5. 还核查了 `DefaultRedstoneWireEvaluator.updatePowerStrength`：线强度改变时，偏移 57–159 对线自身及六邻格逐个调用 `updateNeighborsAt`；其中包含支撑格 C，因而通知 C 周围的 T。此条是默认求值器的更新路径证据，不声称已测试服务器的全部实验性求值模式。

故上述方案的稳态规则成立：不必仅为 T 另加一根红石火把。它是否适用于 V14 实际 S2，要继续核对导线供电路径、衰减、支撑块导电性、碰撞与跨线路干扰。不能以 JSON 中临时填入 `power=15` 来代替真的电源和通电验证。

## G. 门片碰撞厚度与朝向

本节同样是静态代码与资源核查，不是运行游戏得到的碰撞实验。

- `DoorBlock` 静态初始化偏移 30–45 和 `TrapDoorBlock` 静态初始化偏移 24–39 都使用 `Block.boxZ(16,13,16)` 构造基准形状。沿 `Block.boxZ` 三、四、五参数重载追到 `Block.box`，所得范围是像素单位 `(0,0,13)…(16,16,16)`，而 `Block.box` 将六个坐标各除以 16。因此厚度确为 **3/16 格**。
- `Shapes.rotateHorizontal` 和 `Shapes.rotateAll` 都把此基准形状放入 NORTH 项；EAST 项采用 `OctahedralGroup.BLOCK_ROT_Y_90`。该常量映射到 `ROT_90_Y_NEG`，其构造为交换 X/Z 并反转 X，因此南侧薄片旋到西侧，而非东侧。旋转以方块中心为基准。
- `TrapDoorBlock.getShape` 偏移 0–51：打开时直接按 FACING 取形状；关闭时 TOP 取 DOWN 项，BOTTOM 取 UP 项。打开后 HALF 不影响碰撞形状。
- `DoorBlock.getShape` 偏移 0–74：关闭按 FACING 取形状；打开且 HINGE=RIGHT 时把 FACING 逆时针转一次，HINGE=LEFT 则顺时针转一次，再取形状。上下半各有同样的局部薄片形状。
- 两类未单独覆写 `getCollisionShape`。`BlockBehaviour.getCollisionShape` 偏移 0–19 在有碰撞的方块上返回该方块 `getShape`，不是按渲染中“透明纹理的空洞”挖空碰撞。

坐标均为方块内局部坐标；未列的两条轴范围都是 `[0,1]`：

| 形状查表键 | 实际薄片范围 |
|---|---|
| NORTH | 南侧，`z ∈ [13/16,1]` |
| EAST | 西侧，`x ∈ [0,3/16]` |
| SOUTH | 北侧，`z ∈ [0,3/16]` |
| WEST | 东侧，`x ∈ [13/16,1]` |
| UP（仅活板门闭合 bottom） | 底部，`y ∈ [0,3/16]` |
| DOWN（仅活板门闭合 top） | 顶部，`y ∈ [13/16,1]` |

因此铁活板门 `facing=east,half=bottom,open=true` **正是西侧** `x ∈ [0,3/16]` 的竖板。原版资源也吻合：`iron_trapdoor.json` 对 east/open 使用 Y=90°，`template_orientable_trapdoor_open.json` 未旋转门片为 `(0,0,13)…(16,16,16)`。

对普通门举例：`facing=north,open=false` 时是南侧 Z 薄片；同一门 `open=true,hinge=left` 时改为西侧 X 薄片；`hinge=right` 时改为东侧 X 薄片。`3/16=0.1875`，单侧薄片剩余宽度为 `13/16=0.8125`。但“剩余宽度大于玩家宽度”本身仍不是通行证据，门柱、门框、前后方转弯、上下平台均可能参与碰撞。应检查完整连续扫掠体积，不能只检查中心点所在方块是否为空。

### S2：上廊导线控制井口

落地校正（主实现补记）：以下6格为研究时的早期拟议坐标。V14已将拉杆/附着座北移至Z=-4，并把导线延长为Z=-4…2共7格；终端/梯口坐标和供电、攀爬规则不变。拉杆座下增一格接原楼板。准确施工以shortcuts_v14/施工与材料.md为准，不能按早期6格表漏掉首线。

- 连续 6 格红石线：`(-47,34,z)`，`z=-3,-2,-1,0,1,2`。
- 终端线下原支撑：`(-47,33,2)`。
- 铁活板门：`(-46,33,2)`，`facing=east`；正下方普通梯子也为 `facing=east`。

依照 F 节：终端红石线确实有电且原支撑导电时，能强充能其下支撑，再为东邻铁活板门供电。依照 C 节：活板门打开、正下梯子同向时，活板门格可被判为可攀爬。依照 G 节：打开的 east 门片在该格西侧，即世界 X 范围 `[-46,-45.8125]`、Y `[33,34]`、Z `[2,3]`。这是计算井口扫掠碰撞时应采用的门片位置。

六格线“画成连续”不自动证明带电：还应有合法支撑、真实输入，复核线路衰减与附近导电块可能造成的串电。关闭与开启两种状态都要验证常规路线可达、井口实际可通行或被预期门片阻隔。

## 落地验证清单与未证实项

本规则核查可用于设计，但不替代机关本身验收。后续实现至少应覆盖：

- 默认关闭、第一次从内侧拨开、开放状态双向通过、再次关门、再次开启。
- 拉杆默认关门时仍能从原常规路线到达；开关位置不能从封闭捷径入口直接伸手触及，否则不构成预期探索解锁。
- 铁门上下半状态一致、支撑可靠；梯子背板与朝向正确，铁活板门打开后能爬过并离开井口。
- 供电块与门精确六面相邻，中继器输入输出明确，线路有真实电源而非只画出带电外观。
- 新电源及可能被强充能的邻块不接触旧音乐电路；不能仅检查“没有覆盖旧方块”就认定不会串电。
- 独立创意测试世界中完成开关和邻居更新测试；若需要到朋友服务器验收，还须确认该服版本及是否修改红石规则。**本次未执行这些游戏测试。**
